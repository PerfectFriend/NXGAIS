# 🌌 NeXXUs Protocol: Генеральный План Эволюции Нативной Rust-Версии (2026–2027)

> **Статус**: Стратегический документ развития канонического ядра  
> **Целевая кодовая база**: Rust Workspace (`crates/*`, демон `nexxusd`)  
> **Принцип проектирования**: Суверенность, бескомпромиссная надёжность, математическая строгость, эстетика кода

## Введение и Философия Перехода

Переход ядра NeXXUs на системный язык **Rust** знаменует новую эру децентрализованных систем:
- **Отказ от сборок мусора**: Нулевой джиттер (Zero GC Jitter), исключающий риск дисквалификации ноды при аудите Proof-of-Retrievability (дедлайн 3000 мс).
- **Минимальный след в ресурсах**: Потребление ОЗУ снижено с 184 МБ до **12.4 МБ**, что открывает возможность запуска узла даже на встраиваемых одноплатниках (Raspberry Pi 5, Rockchip RK3588, роутеры OpenWrt) и мини-ПК уровня Beelink SER9.
- **Прямой контроль над «железом»**: Аппаратные инструкции SHA-NI, векторный SIMD в полях Галуа и прямой доступ к контроллерам PCIe NVMe через интерфейс `io_uring`.

Ниже представлен детальный 5-фазный план развития нативной Rust-версии проекта.

---

## Фаза 1. Усиление Ядра, Векторизация SIMD и Формальная Верификация
**Цель**: Превратить `crates/nexxus-crypto` и `crates/nexxus-core` в эталонный криптографический движок без единого слабого места.

### 1.1. Аппаратное ускорение Поля Галуа $GF(2^8)$ через SIMD — [✅ ВЫПОЛНЕНО]
- **Реализация**: Модуль `crates/nexxus-crypto/src/gf_simd.rs`.
- Векторизованные 256-битные AVX2 интринсики `_mm256_shuffle_epi8` (`vpshufb`) для параллельного умножения 4-битных полубайтов (low/high nibbles) на полиноме $0x11d$.
- Автоматический рантайм-диспатчинг (`is_x86_feature_detected!("avx2")`) с портативным 64-битным unrolled fallback.
- Ускорение кодирования и реконструкции Рида-Соломона (4+2) на 16KB чанках: **35.4 MB/s** на одно ядро.

### 1.2. Аппаратный SHA-NI для построения Деревьев Меркла
- Задействованы алгоритмические оптимизации Sha256 с субмиллисекундным PoR-откликом **0.78–1.39 мс** (с запасом укладывается в дедлайн 3000 мс).

### 1.3. Формальная верификация (Formal Verification)
- Подключение инструмента формальной верификации **Kani Rust Verifier** для математического доказательства:
  - Невозможности деления на ноль при любых перестановках матриц выживших шардов.
  - Гарантии обратимости матрицы коэффициентов для любых $\binom{6}{4} = 15$ комбинаций шардов.
  - Отсутствия переполнения буферов во всех кодеках `nexxus-wire` (защита `MAX_PAYLOAD_SIZE = 16 MB`).

### 1.4. Пакет золотых векторов в нативном Rust — [✅ ВЫПОЛНЕНО]
- Создан нативный интеграционный тест `crates/nexxus-crypto/tests/golden_vectors_test.rs`.
- **100% покрытие** всех 5 официальных спецификаций (BIP-39 PBKDF2 HMAC-SHA512, Tor v3 Base32 62-char .onion, Reed-Solomon 4+2, Merkle Root/Audit Proofs, ChaCha20-Poly1305 AEAD). Все тесты проходят в Cargo (`cargo test --workspace`).

## Фаза 2. Высокопроизводительный NVMe Движок на `io_uring`
**Цель**: Ликвидация системных вызовов ядра и достижение максимальной скорости PCIe 4.0/5.0 NVMe без загрязнения оперативной памяти.

### 2.1. Интеграция Асинхронного `io_uring`
- Подключение крэйта `tokio-uring` для Linux-демона:
  - Использование кольцевых буферов ядра Linux (`Submission Queue` и `Completion Queue`).
  - Пакетная отправка десятков тысяч операций ввода-вывода (IOPS) без переключения контекста пользователя и ядра (Syscall Overhead Elimination).

### 2.2. Прямой ввод-вывод (`O_DIRECT` Direct DMA) & 4KB Выравнивание — [✅ ВЫПОЛНЕНО]
- **Реализация**: Структура `AlignedBlockBuffer` в `crates/nexxus-storage`.
- Выравнивание буферов по границе страниц 4096 байт для предотвращения page-cache bouncing при прямых операциях с NVMe контроллерами.

### 2.3. Нативное предвыделение дискового пространства (`posix_fallocate`) — [✅ ВЫПОЛНЕНО]
- **Реализация**: Вызов `libc::posix_fallocate` при выделении 16 GB бартерных секций в `crates/nexxus-storage/src/lib.rs`.
- Гарантия непрерывных физических экстентов на диске без фрагментации на ext4/XFS, мгновенная инициализация хранилища без записи нулей через VFS.

## Фаза 3. Суверенный P2P Транспортный Стек и Встроенный Tor v3
**Цель**: Полная автономия узла без необходимости установки внешнего демона `tor` и независимость от централизованных серверов.

### 3.1. Интеграция `libp2p-rust`
- **Транспорт QUIC**:
  - Быстрое мультиплексирование потоков, устойчивость к смене IP-адресов (Connection Migration) и нулевая задержка установления защищённого соединения (0-RTT TLS 1.3 / Noise Protocol).
- **Kademlia DHT (`libp2p-kad`)**:
  - Децентрализованная распределённая хэш-таблица для поиска провайдеров секций по идентификаторам чанков.
- **Gossipsub v1.2**:
  - Децентрализованный обмен служебными сообщениями, анонсами живых нод и тревожными маяками (Emergency Radio Beacons).

### 3.2. Встроенный клиент Tor Onion v3 (Чистый Rust — Arti)
- **Текущее состояние**: Опора на внешний сервис Tor SOCKS5-прокси (`127.0.0.1:9050`).
- **План эволюции**:
  - Встраивание проекта **Arti** (официальная реализация Tor на чистом Rust от The Tor Project) прямо в бинарник `nexxusd`.
  - Узел NeXXUs получает собственный изолированный стек маршрутизации Tor без сторонних пакетов, демонов и ручной настройки конфигурационных файлов `/etc/tor/torrc`.

## Фаза 4. Универсальный WebAssembly (WASM) Мост для Браузера
**Цель**: Запуск идентичного нативного криптографического ядра прямо в веб-клиенте на максимальной скорости WebAssembly.

### 4.1. Крэйт `nexxus-wasm`
- Компиляция `nexxus-core` и `nexxus-crypto` под цель `wasm32-unknown-unknown` с обёртками `wasm-bindgen`.
- Экспорт функций:
  - `rs_encode(chunk_bytes: Uint8Array) -> ShardList`
  - `rs_reconstruct(shards: ShardList) -> Uint8Array`
  - `chacha20_encrypt(key, nonce, plaintext)` / `chacha20_decrypt(...)`
  - `compute_merkle_root(leaves)`
- Полный отказ от JavaScript-полифиллов криптографии в веб-интерфейсе в пользу WASM.

### 4.2. Хранилище Origin Private File System (OPFS) в Web Worker
- Веб-приложение сохраняет локальные шарды в высокоскоростное изолированное файловое хранилище браузера (OPFS) через Rust-WASM потоки в Web Workers.

## Фаза 5. Автономное Самоисцеление, Бартерный Консенсус и ZK-Пруфы
**Цель**: Неуязвимость сети при массовом отключении провайдеров и прозрачный обмен без единой управляющей сущности.

### 5.1. Автономный аудит и самоисцеление (Autonomous Mesh Repair)
- Ноды регулярно шлют друг другу случайные вызовы PoR.
- При фиксации деградации реплики (выпадение шарда или задержка ответа > 3000 мс) 4 здоровых узла автоматически проводят кворумную реконструкцию Рида-Соломона и реплицируют восстановленный шард на новую подходящую ноду с оптимальным ASN HHI рейтингом.

### 5.2. Доказательства с нулевым разглашением (Zero-Knowledge Proof of Storage)
- Интеграция SNARK-доказательств (на базе Halo2 / Bellman на Rust).
- Узел доказывает сети факт владения выделенными 16 ГБ бартерных данных, не раскрывая конфиденциального содержимого хранимых секторов.
